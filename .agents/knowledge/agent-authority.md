# エージェント権限境界

## Purpose

Tulpa の AI エージェントが「何を自律的に行ってよいか」「何は確認が必要か」「何は行ってはならないか」の
判断基準を整理した知識ノートである。

AIエンジニアリングの進化では、エージェントの実行能力が上がるほど「権限の設計」が重要になる。
自走範囲を広げすぎると取り返しのつかない操作が起き、狭すぎると人間の負荷が増す。
このノートはその境界を明文化し、判断コストを下げることを目的とする。

## 権限の3層モデル

### 1. 自律実行可（Autonomous）

人間の確認なしに進めてよい操作。

**ローカル読み書き**
- ファイルの読み込み・編集・作成
- `.agents/learnings/` への JSON 記録
- ExecPlan の作成・更新（`.agents/plans/`）

**ローカル実行**
- テスト・lint・ビルドコマンドの実行
- `git add` / `git commit`（意味のある区切りで）
- `.agents/scripts/` の全スクリプト（record, summarize, propose, refresh, audit）
- ローカルブランチの作成

**知識管理**
- `.agents/knowledge/` へのノート追加・更新
- `MEMORY.md` の再生成

### 2. 確認後に実行（Confirm First）

着手前に人間の確認を得ること。迷ったらこの層に分類する。

**リモート操作**
- `git push` / `git push -u origin <branch>`
- PR の作成・更新・コメント投稿

**ドキュメント変更**
- `AGENTS.md` の直接編集（変更提案は `propose_agent_updates.php` で行う）
- `docs/requirements.md` の変更（SSOT のため）
- `CLAUDE.md` の変更

**外部サービス**
- Slack API への書き込み
- Claude API を使った外部向けの生成・送信

**環境操作**
- ブランチの削除
- 本番以外でもマイグレーションの実行（開発環境を共有している場合）

### 3. 原則禁止（Prohibited）

明示的な指示がない限り、いかなる文脈でも行わない。

**Git の破壊的操作**
- `git push --force` / `git push -f`
- `git reset --hard`（ローカルを含む）
- `git commit --no-verify`（フック回避）
- 他者の変更を上書きするリベース

**セキュリティ**
- `.env` や秘密情報を含むファイルのコミット
- 認証・認可ロジックの変更（設計レビューなしに）
- セキュリティ設定の変更

**本番環境**
- 本番DBへの直接操作
- 本番サーバーへの直接デプロイ

## エスカレーション基準

次の状況では作業を止めて人間に判断を仰ぐ。

| 状況 | 理由 |
|------|------|
| 設計の前提が崩れる発見 | `open-questions.md` 追加が必要なレベル |
| 複数の有効な選択肢があり方針が未定 | 誤った選択が後工程に波及する |
| MVP スコープ外の実装要求 | フェーズ境界を守るため |
| セキュリティ・個人情報・法令に関わる判断 | 専門知識と責任が必要 |
| ExecPlan なしに複数ファイル横断の大変更 | 設計なしの大規模変更はリスクが高い |
| 「壊れた状態」でコミットせざるを得ない状況 | 例外対応の記録が必要 |

## 権限境界の更新方針

この境界は固定ルールではなく、運用経験を通じて細かくなっていくもの。

- 新しい判断事例が出たら `.agents/learnings/` に記録する
- 同じケースが 2 回以上発生したらこのノートへの昇格を検討する
- 「禁止」層への追加は慎重に。過度な制約はエージェントの有用性を下げる
- 「自律実行可」の範囲を広げるときは、取り消し可能な操作かどうかを必ず確認する
