# エージェント権限境界

## Purpose

Tulpa の AI エージェントが「何を自律的に行ってよいか」「何は確認が必要か」「何は行ってはならないか」の
判断基準を整理した知識ノートである。

AIエンジニアリングの進化では、エージェントの実行能力が上がるほど「権限の設計」が重要になる。
自走範囲を広げすぎると取り返しのつかない操作が起き、狭すぎると人間の負荷が増す。
このノートはその境界を明文化し、判断コストを下げることを目的とする。

## 権限の3層モデル

### 1. 自律実行可（Autonomous）

人間の確認なしに進めてよい操作。

**ローカル読み書き**
- ファイルの読み込み・編集・作成
- `.agents/learnings/` への JSON 記録
- ExecPlan の作成・更新（`.agents/plans/`）

**ローカル実行**
- テスト・lint・ビルドコマンドの実行
- `git add` / `git commit`（意味のある区切りで）
- `.agents/scripts/` の全スクリプト（record, summarize, propose, refresh, audit）
- ローカルブランチの作成

**知識管理**
- `.agents/knowledge/` へのノート追加・更新
- `MEMORY.md` の再生成

### 2. 確認後に実行（Confirm First）

着手前に人間の確認を得ること。迷ったらこの層に分類する。

**リモート操作**
- `git push` / `git push -u origin <branch>`
- PR の作成・更新・コメント投稿

**ドキュメント変更**
- `AGENTS.md` の直接編集（変更提案は `propose_agent_updates.php` で行う）
- `docs/requirements.md` の変更（SSOT のため）
- `CLAUDE.md` の変更

**外部サービス**
- Slack API への書き込み
- Claude API を使った外部向けの生成・送信

**環境操作**
- ブランチの削除
- 本番以外でもマイグレーションの実行（開発環境を共有している場合）

### 3. 原則禁止（Prohibited）

明示的な指示がない限り、いかなる文脈でも行わない。

**Git の破壊的操作**
- `git push --force` / `git push -f`
- `git reset --hard`（ローカルを含む）
- `git commit --no-verify`（フック回避）
- 他者の変更を上書きするリベース

**セキュリティ**
- `.env` や秘密情報を含むファイルのコミット
- 認証・認可ロジックの変更（設計レビューなしに）
- セキュリティ設定の変更

**本番環境**
- 本番DBへの直接操作
- 本番サーバーへの直接デプロイ

## エスカレーション基準

次の状況では作業を止めて人間に判断を仰ぐ。

| 状況 | 理由 |
|------|------|
| 設計の前提が崩れる発見 | `open-questions.md` 追加が必要なレベル |
| 複数の有効な選択肢があり方針が未定 | 誤った選択が後工程に波及する |
| MVP スコープ外の実装要求 | フェーズ境界を守るため |
| セキュリティ・個人情報・法令に関わる判断 | 専門知識と責任が必要 |
| ExecPlan なしに複数ファイル横断の大変更 | 設計なしの大規模変更はリスクが高い |
| 「壊れた状態」でコミットせざるを得ない状況 | 例外対応の記録が必要 |

## Safe Authority Loop — ゴール設計の注意点

権限を与えるだけでは不十分で、「何を達成してよいか（ゴール）」の設計も同等に重要である。

**問題のパターン**: 「テストをパスせよ」と指示したとき、最短経路が「テストコードを削除する」になることがある。
これはエージェントの能力不足ではなく、ゴール設計の失敗である。

Tulpa でのゴール設計原則:

- 手段ではなく **意図** を指示する。「このファイルを修正せよ」より「この機能が正しく動くようにせよ」
- 制約を明示する。「テストを削除・変更せずに」「既存の設計原則を壊さずに」
- 検証可能な受け入れ基準を与える。ExecPlan の「Validation and Acceptance」セクションがこれに対応する
- 自律ループに入るとき（例: テスト失敗 → 修正 → 再テスト のサイクル）はループの終了条件を先に定める

## 段階的な信頼移譲（Graduated Trust Delegation）

権限の境界は固定ではなく、実績に応じて変化させる設計が望ましい。

### 自律度レベル

| レベル | 説明 | 対象フェーズ |
|-------|------|------------|
| **A — 提案のみ** | 変更案を示すが実行しない。人間が承認してから実行 | 未知のドメイン・初回着手時 |
| **B — 実行＋報告** | 自律実行するが、完了後に必ず差分・理由・判断根拠を報告する | 慣れたドメイン・繰り返し作業 |
| **C — 自律完結** | 実行・確認・コミットまで完結。大きな区切りでのみ報告する | 実績のある定型作業のみ |

### レベル昇格の基準

「自律実行可」の範囲を広げるときは、次の基準を満たしていること。

- 同種の作業を 3 回以上 B レベルで完遂し、手戻りが発生していない
- 該当ドメインの設計原則（AGENTS.md・設計書）を正確に参照できている
- 取り消し可能な操作である（ファイル変更・コミットは可逆、force push は不可逆）

### Autonomy Certificate（自律性証明書）

エージェントセッション開始時に「この作業の自律度レベル」を明示することで、
過剰な確認や過剰な自走を防ぐ。

ExecPlan の冒頭に記載する例:
```
Autonomy Level: B（実行＋報告）
Scope: app/Services/ 以下のサービスクラス追加のみ
Excluded: データベースマイグレーション実行、AGENTS.md の変更
```

## 権限境界の更新方針

この境界は固定ではなく、運用経験で細かくなっていくもの。

- 新しい判断事例が出たら `.agents/learnings/` に記録する
- 同じケースが 2 回以上発生したらこのノートへの昇格を検討する
- 「禁止」層への追加は慎重に。過度な制約はエージェントの有用性を下げる
- レベル昇格は「実績の蓄積」を根拠にする。信頼は宣言でなく経験で積む
