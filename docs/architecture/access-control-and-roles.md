# 権限とアクセス境界の設計メモ

このドキュメントは [要件定義書](../requirements.md) の 3 章「ユーザーと権限」と、4 章・5 章に散在する閲覧主体の条件をまとめた補助設計書です。Tulpa の 4 ロールがどの情報を見て、どの操作を行い、どこでアクセスを止めるかを実装向けに整理します。

---

## 1. 対象範囲

このメモでは次の内容を扱います。

1. 4 ロールの基本責務とアクセス境界
2. ロール別に閲覧・作成・更新できる主要データ
3. 強いアクセス制御が必要な情報
4. 将来機能を追加する際の判断基準

認証方式そのもの、招待メールの実装、Laravel のミドルウェア構成詳細は別設計対象とします。

---

## 2. 基本方針

Tulpa は 1 エージェント会社での利用を前提とし、複雑な権限マトリクスを採用しません。ロールは `owner`、`agent`、`engineer`、`client_contact` の 4 つに固定し、基本ルールを崩さない形で実装します。

- オーナーはシステム全体を管理する
- エージェントは案件・契約・提案活動の実務を担う
- エンジニアは自分自身に関する情報だけを扱う
- クライアント担当者は自社案件の稼働確認だけに関与する

「見えてよいか」を先に判定し、その後で「編集してよいか」を判定します。特に口座情報、契約条件、外部連携トークン、内部メモは一般情報と同列に扱いません。

---

## 3. ロール別アクセス境界

### 3.1 オーナー

オーナーはシステム設定と全体管理を担うため、全ロールの中で最も広い閲覧権限を持ちます。ただし、日常運用の実務を前提にしないため、案件操作や面談メモ記録の中心的な担い手としては扱いません。

- 閲覧: 全クライアント、全案件、全契約、全稼働報告、全支払通知、全設定
- 作成・更新: エージェント招待、システム設定、連携設定、緊急時の全体データ補正
- 制約: オーナー権限の存在を理由に通常運用フローを省略しない

### 3.2 エージェント

エージェントは Tulpa の中核利用者です。案件、契約、見込みエンジニア、正式登録済みエンジニア、稼働確認、提案活動に横断的にアクセスします。

- 閲覧: 全クライアント、全案件、全契約、全エンジニア、見込みエンジニア、稼働報告
- 作成・更新: 案件、契約、面談メモ、初回連絡履歴、差戻しコメント
- Phase 2 以降: 支払通知、請求書
- Phase 3 以降: AI サマリー、AI 関連ログ
- 制約: エンジニア本人しか更新しない情報は直接上書きしない設計を優先する

### 3.3 エンジニア

エンジニアは自分に紐付くデータだけを扱います。閲覧範囲は狭く、入力主体としての自律性を守る設計を優先します。

- 閲覧: 自分の契約概要、自分の稼働記録、自分の月次稼働報告、自分のスキルシート
- 作成・更新: 稼働記録、月次報告の提出、スキルシート、振込先情報、面談後補足メモ
- Phase 2 以降: 自分の支払通知
- Phase 3 以降: 公開プロフィール設定、AI 出力の一部
- 制約: 他エンジニアの情報、クライアント内部情報、非公開の営業メモは見えない

### 3.4 クライアント担当者

クライアント担当者は MVP では稼働確認フローに必要な最小権限だけを持ちます。営業情報や他社情報へはアクセスさせません。

- 閲覧: 自社案件に紐付く確認待ちの稼働報告、関連する対象月、自分が担当する案件の案件名、対象エンジニアの識別情報
- 作成・更新: 稼働報告の確認、差戻しコメントの記録
- 制約: 契約単価、支払通知、他クライアント案件、社内用メモ、他担当者一覧、公開前の候補者サマリーは見えない

## 4. 主要データごとの閲覧・操作原則

| データ | owner | agent | engineer | client_contact |
|------|------|------|------|------|
| Client | 全件可 | 全件可 | 不可 | 自社の基本情報のみ閲覧可 |
| ClientContact | 全件可 | 全件可 | 不可 | 自分自身のアカウント情報のみ閲覧可 |
| Project | 全件可 | 全件可 | MVP では自分に関連する案件のみ | 自社関連のみ |
| Contract | 全件可 | 全件可 | 自分に関連する契約のみ | 原則不可 |
| WorkRecord | 全件可 | 関連案件を閲覧可 | 自分の記録のみ編集可 | 不可 |
| WorkReport | 全件可 | 全件可 | 自分の報告のみ編集・提出可 | 自社案件分のみ確認可 |
| PaymentNotice / Invoice | 全件可 | Phase 2 以降可 | Phase 2 以降、自分の支払通知のみ閲覧可 | 不可 |
| EngineerLead | 全件可 | 全件可 | 自分が登録者本人である場合の入力内容のみ可 | 不可 |
| InterviewNote | 全件可 | 全件可 | `audience=engineer` のみ閲覧可。内部メモは不可 | 不可 |
| PublicProfile | 全件可 | Phase 3 以降、関連エンジニア分可 | Phase 3 以降、自分のみ設定可 | 公開 URL のみ閲覧可 |
| AI ログ | 全件可 | Phase 3 以降、実務上必要な範囲で可 | Phase 3 以降、自分に関する出力の一部可 | 不可 |

補足:

- `ClientContact` は `User` と `Client` を分離して保持し、無効化しても履歴を残します。
- `InterviewNote` は `audience` に応じて表示範囲を制御し、内部メモを誤って公開しないことを優先します。
- 公開プロフィールは URL が公開されても、内部データとは別経路で生成される前提にします。

---

## 5. 強いアクセス制御が必要な情報

次の情報は、通常のプロフィール情報より一段強い制御をかける対象です。

- 銀行口座情報
- 契約単価、精算幅、支払いサイト
- Claude API キー、Slack OAuth トークンなどの機密情報
- エージェントの内部面談メモ、評価メモ、営業メモ
- 公開前の候補者サマリー、AI 下書き、外部共有前の文章

この種の情報は「関連があるから見せる」ではなく、「そのロールの責務に不可欠か」で判定します。たとえばクライアント担当者には稼働報告の確認は必要ですが、単価や支払いサイトは不要なので見せません。

---

## 6. 実装時の判断ルール

### 6.1 ロール追加を安易に行わない

MVP では 4 ロールで運用を完結させます。要件書で対象外としている複雑な組織分離や細粒度 RBAC を先回りで導入しません。

### 6.2 会社境界より責務境界を優先する

Tulpa は単一エージェント会社利用を前提とするため、エージェント内部の全案件をエージェント全員が扱えるシンプルさを優先します。部署別の閲覧制限や案件単位 ACL は初期版では持ち込みません。

### 6.3 公開機能は内部画面と別物として扱う

公開プロフィールや外部共有 URL は、内部画面の一部をそのまま見せる設計にしません。公開可否を個別に確認した項目だけで再構成します。

---

## 7. 受け入れ条件

この設計メモに基づく実装の完了条件は次のとおりです。

1. 4 ロールのアクセス境界を、画面遷移とデータ取得の両方で説明できる。
2. クライアント担当者が自社案件の稼働報告だけを確認でき、契約条件や内部メモは見えない。
3. エンジニアが自分の稼働・契約・支払情報だけを扱え、他人のデータへアクセスできない。
4. 公開プロフィールの表示内容が、内部の非公開情報から明確に分離されている。
