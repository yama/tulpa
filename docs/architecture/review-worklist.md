# MVP 文書レビュー作業表

このドキュメントは、Tulpa の MVP で先に固めるべき文書を順番にレビューするための作業表です。人が読むための一覧であると同時に、AI エージェントがどの文書から確認を始めるかを迷わないための実行順でもあります。

---

## 1. 使い方

レビューは次の順で進めます。

1. 対象文書の目的を確認する
2. レビュー観点に沿って曖昧さや不足を洗い出す
3. 未決事項チェックを埋める
4. 必要なら `notes/` に個別論点メモを追加する
5. 受け入れ条件が読める状態になったら次へ進む

AI が自走で実装を進める前提では、各文書について「未決事項が残っているか」を必ず先に確認します。未決が大きいまま実装へ進まないことを原則にします。

## 3. 文書別レビュー表

### 3.1 [requirements.md](../requirements.md)

目的:
Tulpa 全体の要件、用語、MVP と将来フェーズの境界を管理する SSOT。

レビュー観点:

- MVP / Phase 2 / Phase 3 の記述が混線していないか
- Out of Scope が本当に除外境界として機能しているか
- AGENTS.md の用語とズレていないか
- 非機能要件の数値や仮置きがレビュー可能な粒度か

未決事項チェック:

- MVP に残す機能と後続フェーズへ送る機能が明確か
- 将来機能を本文にどこまで残すかの方針が決まっているか
- 非機能要件の仮置き数値に暫定であることが明示されているか

完了条件:

- MVP 境界を読んだ人が、実装対象と対象外を区別できる
- 用語と責任境界に矛盾がない

### 3.2 [access-control-and-roles.md](./access-control-and-roles.md)

目的:
4 ロールの責務、閲覧範囲、操作範囲を固定する。

レビュー観点:

- 4 ロールで MVP が回るか
- 誰が見えるかと誰が編集できるかが分かれて書かれているか
- 強いアクセス制御対象が漏れていないか
- クライアント担当者向け境界が広がりすぎていないか

未決事項チェック:

- クライアント担当者に見せる項目の最小集合が決まっているか
- エージェントの横断権限の範囲が明確か
- 面談メモや営業メモの公開境界が固定されているか

完了条件:

- 各ロールが「見えるもの」「更新するもの」を一文で説明できる
- 口座情報、契約条件、内部メモの保護方針が読める

### 3.3 [data-model.md](./data-model.md)

目的:
MVP で扱う主要エンティティ、参照関係、履歴保持の境界を固定する。

レビュー観点:

- エンティティ責務が重複していないか
- 見込みデータと確定データが混ざっていないか
- 履歴保持が必要な対象が漏れていないか
- MVP と将来拡張のモデルが一体化していないか

未決事項チェック:

- `EngineerLead` から `Engineer` へ何を引き継ぐか決まっているか
- `SkillSheet` を独立モデルにする理由が十分か
- `Invoice` と `PaymentNotice` を MVP 対象外としてどう扱うか明確か

完了条件:

- 主要エンティティの責務を人と AI の両方が誤読しにくい
- MVP 実装時に先回りした複雑化を避けられる

### 3.4 [work-record-and-report-design.md](./workflows/work-record-and-report-design.md)

目的:
稼働記録の入力と月次稼働報告の状態遷移を固定する。

レビュー観点:

- 状態遷移が一意に読めるか
- 即時入力と後入力の整合が取れているか
- 編集可能期間と差戻し条件が明確か
- 契約期間との整合性が崩れていないか

未決事項チェック:

- 休憩時間を MVP でどこまで扱うか決まっているか
- 日跨ぎ稼働を MVP で許容するか決まっているか
- 差戻し時に修正できる単位が明確か
- 提出締めの運用ルールが必要か判断できているか

完了条件:

- `draft`、`submitted`、`returned`、`confirmed` の扱いが明確
- 稼働記録修正と月次報告修正が混同されていない

### 3.5 [project-contract-lifecycle.md](./workflows/project-contract-lifecycle.md)

目的:
クライアント、案件、契約、契約履歴、更新・終了時の扱いを固定する。

レビュー観点:

- `Client -> Project -> Contract` の流れが崩れていないか
- 契約履歴が上書きで失われない前提になっているか
- 請求向け条件と支払向け条件の参照先が明確か
- 契約終了後の稼働入力停止が読み取れるか

未決事項チェック:

- 月途中の契約変更を MVP でどう扱うか
- 契約更新時の UI をどこまで要件化するか
- 案件終了と契約終了がズレるケースをどう吸収するか
- 直請け案件の最小要件が明確か

完了条件:

- 契約条件の履歴と参照先が説明できる
- 過去月の計算根拠を失わない原則が明文化されている

### 3.6 [ui-and-screen-design.md](./ui-and-screen-design.md)

目的:
ロール別の主要画面、導線、MVP で持つべき画面数を固定する。

レビュー観点:

- 画面の数が MVP に対して多すぎないか
- ダッシュボードが情報過多になっていないか
- ロール別の主導線が 3 ステップ程度で追えるか
- クライアント担当者向け画面が最小構成に留まっているか

未決事項チェック:

- エージェント向けナビゲーションの最小項目が決まっているか
- 年間カレンダービューの優先度が本当に MVP 相当か
- 公開プロフィール画面を MVP 対象外として十分に切れているか

完了条件:

- 「画面設計はどこか」に対してこの文書を案内できる
- 各ロールの主要画面と主目的を簡潔に説明できる

---

## 4. AI 自走前チェック

AI エージェントが実装に入る前に、少なくとも次を確認します。

- 対象文書の未決事項が空か、実装に影響しないレベルまで縮んでいる
- 要件書と設計書の間に矛盾がない
- 対象外の将来機能が MVP 設計へ混入していない
- 受け入れ条件が、動作または画面確認として読める

未決事項が大きい場合は、実装ではなく文書更新を先に行います。

---

## 5. 補助メモの追加ルール

レビュー中に単一論点だけが詰まった場合は、`docs/notes/` に補助メモを追加します。次のようなケースです。

- 特定カラムや Enum の値だけ判断が必要
- 単一画面の挙動だけを先に決めたい
- フロー全体ではなく一部の例外処理だけを切り出したい

複数文書にまたがる判断なら、`notes/` ではなく `architecture/` 側へ戻して整備します。
