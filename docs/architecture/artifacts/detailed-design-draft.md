## 3. 対象機能

1. 稼働記録の登録・修正
2. 月次稼働報告の提出・確認

この 2 機能は、Tulpa の「契約を起点に稼働データがつながる」特徴を最も表しやすいため、先に詳細化します。

---

## 4. 詳細設計 1: 稼働記録の登録・修正

### 3.1 目的

エンジニアが契約に紐づく稼働記録を登録し、必要時には履歴付きで修正できるようにする。

### 3.2 主体

- 実行主体: エンジニア
- 補助主体: エージェント
- 参照主体: 必要に応じてクライアント担当者

### 3.3 事前条件

- 対象エンジニアに有効な `Contract` が存在する
- 対象日が契約期間内である
- 月次稼働報告が `confirmed` で固定済みの場合、修正可否は別途運用ルールに従う

### 3.4 入力

| 項目 | 型 | 必須 | 備考 |
|------|------|------|------|
| `contract_id` | bigint | 必須 | 契約選択または自動補完 |
| `work_date` | date | 必須 | 稼働日 |
| `started_at` | datetime | 必須 | 作業開始 |
| `ended_at` | datetime | 必須 | 作業終了 |
| `memo` | text | 任意 | 補足 |
| `revision_reason` | text | 条件付き必須 | 修正時のみ必須 |

### 3.5 基本フロー

1. エンジニアが稼働記録入力画面を開く
2. システムが当日または対象日の有効契約を候補表示する
3. エンジニアが作業開始・作業終了を入力する
4. サーバー側で契約期間、時刻整合、権限を検証する
5. 新規登録なら `work_records` を作成する
6. 修正なら `work_record_revisions` を保存してから `work_records` を更新する
7. 更新後、対象月の月次稼働報告集計に反映する

### 3.6 バリデーション

| 項目 | ルール | 備考 |
|------|------|------|
| `contract_id` | 自分がアクセス可能な契約であること | 権限必須 |
| `work_date` | 契約期間内であること | 境界条件あり |
| `started_at` | `ended_at` より前であること | 日跨ぎは未確定 |
| `ended_at` | `started_at` より後であること |  |
| `revision_reason` | 修正時は 1 文字以上 | ダミーの最小条件 |

### 3.7 例外系

| ケース | 振る舞い |
|------|------|
| 契約期間外 | 登録不可。メッセージを返す |
| 他人の契約 | 403 相当 |
| 確認済み月の修正 | 初期版では不可または差戻し前提。未確定 |
| 同日重複入力 | 初期版では警告または上書き禁止。未確定 |

### 3.8 関連テーブル

- `contracts`
- `work_records`
- `work_record_revisions`
- `work_reports`

### 3.9 I/O の暫定イメージ

リクエスト:

```text
POST /work-records
PATCH /work-records/{id}
```

レスポンス:

- 成功時は詳細画面または一覧部分を再描画
- 失敗時は同画面にバリデーションエラーを表示

### 3.10 ダミーを含む箇所

- ルート設計は仮置き
- 同日重複入力の扱いは未確定
- 確認済み月の修正ポリシーは運用確定待ち

## 5. 詳細設計 2: 月次稼働報告の提出・確認

### 4.1 目的

対象月の稼働記録を月次稼働報告としてまとめ、エンジニア提出とクライアント担当者確認を成立させる。

### 4.2 主体

- 提出主体: エンジニア
- 確認主体: クライアント担当者
- 補助主体: エージェント

### 4.3 状態

| 状態 | 意味 |
|------|------|
| `draft` | 集計中、未提出 |
| `submitted` | エンジニアが提出済み |
| `returned` | クライアント担当者が差戻し |
| `confirmed` | クライアント担当者が確認済み |

### 4.4 入力

| 項目 | 型 | 必須 | 備考 |
|------|------|------|------|
| `target_month` | string | 必須 | `YYYY-MM` 想定 |
| `client_comment` | text | 任意 | 差戻し理由や確認コメント |
| `action` | string | 必須 | `submit`, `return`, `confirm` の仮置き |

### 4.5 基本フロー

1. エンジニアが対象月の詳細画面を開く
2. システムが `work_records` を集計し、対象月の暫定合計を表示する
3. エンジニアが提出すると `submitted` へ遷移する
4. クライアント担当者が内容を確認する
5. 問題なければ `confirmed`、修正が必要なら `returned` とする
6. `returned` の場合、エンジニアが稼働記録またはコメントを見直して再提出する

### 4.6 状態遷移ルール

| 現在状態 | 操作 | 次状態 | 備考 |
|------|------|------|------|
| `draft` | 提出 | `submitted` | エンジニアのみ |
| `submitted` | 差戻し | `returned` | クライアント担当者のみ |
| `submitted` | 確認 | `confirmed` | クライアント担当者のみ |
| `returned` | 再提出 | `submitted` | エンジニアのみ |

### 4.7 バリデーション

| 項目 | ルール | 備考 |
|------|------|------|
| 提出 | 対象月に稼働記録が存在すること | 最小条件 |
| 確認 | 自分が対象契約を確認できること | 権限必須 |
| 差戻し | `client_comment` を必須にしてよいかは未確定 | 現状は推奨 |

### 4.8 例外系

| ケース | 振る舞い |
|------|------|
| 稼働記録が 0 件 | 提出不可または警告付き提出。未確定 |
| 権限外ユーザーの確認操作 | 403 相当 |
| `confirmed` 後の再編集 | 初期版では不可寄り。未確定 |

### 4.9 関連テーブル

- `work_reports`
- `work_records`
- `contracts`

### 4.10 I/O の暫定イメージ

リクエスト:

```text
POST /work-reports/{id}/submit
POST /work-reports/{id}/return
POST /work-reports/{id}/confirm
```

レスポンス:

- 成功時は状態バッジ、コメント欄、集計結果を再描画
- 失敗時は状態遷移不可の理由を表示

### 4.11 ダミーを含む箇所

- ルートは仮置き
- 差戻しコメント必須化は未確定
- 稼働記録 0 件時の扱いは運用確定待ち
