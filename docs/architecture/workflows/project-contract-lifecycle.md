# 案件と契約ライフサイクルの設計メモ

このドキュメントは [要件定義書](../../requirements.md) の 4.2 節「契約管理」、4.8 節「データ整合性ルール」、5.3 節「エージェント向け画面」、7 章「データモデル」をまとめた補助設計書です。Tulpa におけるクライアント、案件、契約、履歴の関係を実装向けに整理します。

---

## 1. 対象範囲

このメモでは次の内容を扱います。

1. クライアントから案件、契約へつながる基本構造
2. 契約の登録単位と履歴保持
3. 契約と稼働・請求支払の連動
4. 契約終了・更新時の扱い

請求書 PDF の見た目、支払計算式、CRM 詳細分析はここでは扱いません。

---

## 2. 基本構造

Tulpa では `Client -> Project -> Contract` の順で文脈を掘り下げます。クライアントと案件だけ、あるいは案件とエンジニアだけを直接つないで終わらせず、契約条件を必ず明示的なレコードとして持ちます。

- `Client` は取引相手の企業
- `Project` はクライアントに紐付く案件
- `Contract` は案件に入るエンジニア単位の契約条件

この構造により、同じクライアントに複数案件がある場合も、同じエンジニアが複数案件に関わる場合も、条件差分を失わずに扱えます。

---

## 3. 案件の役割

`Project` は営業活動と稼働実務をつなぐ中間点です。MVP では、クライアント、案件名、必要スキル、単価レンジ、勤務地、稼働率のような案件本体情報を持つレコードとして扱います。

案件の状態は少なくとも次の観点で追える必要があります。

- 稼働中か
- 終了済みか

MVP では、案件ステータスは「稼働前」「稼働中」「終了」の最低限に留めます。`募集中` `提案中` `公開可否` のような営業活動寄りの属性は Phase 2 以降の拡張として扱います。

---

## 4. 契約の登録単位

### 4.1 1 契約 = 1 エンジニア + 1 案件 + 1 当事者組み合わせ

Tulpa の `Contract` は、法律文書ファイルではなく契約条件レコードです。同じ案件に複数エンジニアが参加する場合は、エンジニアごとに契約を持ちます。

さらに、同じ案件・同じエンジニアでも、誰と誰の条件かで意味が変わるため、`contract_party_type` を持たせます。

- `agent_client`
- `agent_engineer`
- `client_engineer_direct`

この点の詳細は [契約管理・稼働記録の設計メモ](../../notes/contract-work-record-design.md) を参照します。

MVP では、稼働記録と月次稼働報告を成立させるために `agent_engineer` または `client_engineer_direct` のいずれかがあれば開始可能とします。`agent_client` は将来の請求処理で必要になりますが、MVP の稼働開始条件としては必須にしません。

`client_engineer_direct` は MVP でも許容します。ただし、初期版では `agent_engineer` と同じ画面構造で登録できることを優先し、専用の複雑な分岐 UI は持ち込みません。

### 4.2 契約履歴

契約は上書きより履歴を優先します。

- 開始日・終了日を持つ
- 単価、精算幅、支払いサイトは時点ごとに保持する
- 更新時は新しい契約条件レコードを追加し、過去を自動再計算しない
- 注文書 PDF は必要に応じて紐付ける

「最新条件だけを持ち、過去は見ない」設計にはしません。支払通知や請求書の根拠が追えなくなるためです。

---

## 5. 契約と他機能の連動

### 5.1 稼働記録

`WorkRecord` と `WorkReport` は、原則としてエンジニア側の稼働条件を持つ契約を参照します。つまり通常は `agent_engineer` または `client_engineer_direct` が基準です。

### 5.2 請求書

`Invoice` はクライアント向け請求のため、`agent_client` の条件を参照します。クライアントとの請求条件とエンジニアへの支払条件は一致するとは限らないため、明示的に分けます。これは Phase 2 以降の前提ルールです。

### 5.3 支払通知

`PaymentNotice` はエンジニア向け支払のため、`agent_engineer` または `client_engineer_direct` を基準にします。これは Phase 2 以降の前提ルールです。

---

## 6. ライフサイクル上のルール

### 6.1 契約開始前

- 契約未開始の案件には稼働記録を紐付けない
- 契約概要は見えても、稼働入力対象にはしない

### 6.2 契約中

- 稼働記録を受け付ける
- 月次稼働報告を生成・提出できる
- （Phase 2以降）契約更新の 30 日前と 7 日前にエージェントへ通知できる状態を想定する

### 6.3 契約終了後

- 新規の稼働記録は追加できない
- 契約期間中の記録は履歴付きで修正できる
- 契約履歴と対象月の条件は残り続ける

### 6.4 契約更新時

- 過去レコードを直接書き換えず、新しい条件レコードを追加する
- 対象月の請求支払は、その月に有効だった契約条件で固定する
- MVP では月途中の契約条件変更は対象外とし、契約更新は月初から有効になる前提で扱う
- 将来的に月途中の条件変更を扱う場合でも、少なくとも過去確定月を自動再計算しない原則は維持する

## 7. エージェント画面で見えるべきこと

エージェント向け画面では、案件と契約を別々に見るのではなく、クライアント詳細とエンジニア詳細の両方から辿れることが重要です。

- クライアント詳細から、案件一覧、担当者、契約履歴を辿れる
- エンジニア詳細から、現在契約、過去契約、稼働状況を辿れる
- （Phase 2以降）過去提案履歴や支払通知を辿れる
- （Phase 2以降）契約更新や終了が近いものをダッシュボードで把握できる

「どこから見ても案件と契約の文脈に戻れる」ことを、画面設計の原則とします。

---

## 8. 実装時の判断ルール

### 8.1 契約書ファイルと契約条件を混同しない

注文書 PDF がなくても契約条件レコードは必要です。逆に、PDF だけあっても Tulpa 上の契約条件が欠けていてはいけません。

### 8.2 契約終了で履歴を消さない

終了は無効化や過去化であり、削除ではありません。履歴、請求支払根拠、稼働報告との参照が残る必要があります。

### 8.3 CRM 機能に引っ張られすぎない

案件と契約の中心価値は、提案履歴の管理そのものではなく、稼働・請求支払・更新判断を一つの文脈で扱えることにあります。CRM 由来の項目を増やし過ぎて中心責務をぼかさないようにします。

---

## 9. 受け入れ条件

1. `Client -> Project -> Contract` の文脈で案件と契約を辿れる。
2. 同じ案件・同じエンジニアでも、契約当事者組み合わせごとに条件を分けて保持できる。
3. 契約更新後も、過去月の請求支払根拠が失われない。
4. 契約終了後に新規稼働記録は止まり、過去期間の修正は履歴付きで行える。
