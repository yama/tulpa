# データモデル補助設計

このドキュメントは [要件定義書](../requirements.md) の 7 章「データモデル」を、実装判断しやすい単位に整理した補助設計書です。Tulpa が「案件・クライアントを中心にデータが繋がる」構造をどう保持するかを明示します。

---

## 1. 対象範囲

このメモでは次の内容を扱います。

1. 主要エンティティの責務
2. エンティティ間の中心的な参照関係
3. 履歴を別保持すべきデータ
4. MVP と将来拡張の境界

カラム定義の完全版や ER 図の描画形式はここでは固定しません。実際の migration 設計時に、この文書を判断基準として詳細化します。

---

## 2. 中心に置くエンティティ

Tulpa の中心は `Client` と `Project` です。営業活動、契約、稼働、請求、支払はこの軸にぶら下がります。`Engineer` も重要な主体ですが、単独で閉じたプロフィール管理システムにはしません。どの業務データも「どの案件・どのクライアントの文脈か」を辿れる構造を優先します。

主要な軸は次のとおりです。

- `Client` はクライアント企業そのものを表す
- `Project` はクライアントに紐付く案件を表す
- `Contract` は案件に参加するエンジニア単位の契約条件を表す
- `WorkRecord` と `WorkReport` は `Contract` に紐付く
- `Invoice` はクライアント向け、`PaymentNotice` はエンジニア向けの確定データを表す

---

## 3. エンティティ責務

### 3.1 ユーザー系

`User` は認証主体の共通基盤です。ロールはここで保持し、詳細プロフィールは各個別モデルへ分けます。

- `Engineer` はエンジニア本人の業務プロフィール
- `ClientContact` はクライアント企業の担当者
- `EngineerLead` は正式登録前の見込みエンジニア

`EngineerLead` と `Engineer` を分ける理由は、登録フォーム由来の未確定データと、正式運用データを混在させないためです。初回接点管理の履歴も `EngineerLead` 側に寄せます。

正式登録時の引き継ぎは、少なくとも次を対象にします。

- `name`
- `email`
- 登録フォームで受け付けたスキル要約
- 自由記述のプロフィール本文
- 添付ファイルへの参照情報

一方で、初回連絡履歴、面談結果、内部メモは `EngineerLead` 側の履歴として保持し、`Engineer` へ単純コピーしません。正式登録後に参照できる必要はありますが、業務プロフィール本体と混ぜない方針を取ります。

### 3.2 営業・案件系

- `Client`: 取引先企業の基本情報
- `Project`: 必要スキル、単価レンジ、勤務地、稼働率を含む案件本体
- `EngineerApproach` / `ClientApproach`: 軽量 CRM の履歴

営業履歴は案件・クライアント・エンジニアの文脈に紐付きますが、SFA 的な大規模分析対象にはしません。あくまで「次に何をするか」と「何をしたか」を残すための構造に留めます。

MVP では `Client` を CRM の母体として肥大化させず、企業基本情報と担当者紐付けを優先します。`next_action_at` や営業ステータスのような CRM 属性は Phase 2 以降の拡張として扱います。

### 3.3 契約・稼働系

- `Contract`: 契約条件の本体
- `OrderDocument`: 注文書 PDF などの添付
- `WorkRecord`: 日次の最新稼働記録
- `WorkReport`: 月次の提出単位
- `WorkRecordRevision`: 稼働記録の修正履歴

`Contract` は契約書ファイルそのものではなく、単価、精算幅、期間、当事者組み合わせを含む業務データです。`WorkRecord` と `WorkReport` は契約条件の履歴を参照しながら動くため、契約から切り離した集計テーブルとして扱いません。

### 3.4 プロフィール・共有系

- `SkillSheet`: スキルシート本体
- `ActivityLog`: 人手で残すコミュニケーションメモ

`SkillSheet` は MVP の中核です。`Engineer` にすべてを埋め込むのではなく、プロフィールの編集単位として独立させることで、将来の PDF 出力や AI 入力元を追加しても責務を崩しにくくします。

### 3.5 外部連携系

- `AiMatchingLog`: AI 下書きと履歴
- `EngineerActivity`: 外部サービス連携データのキャッシュ
- `PublicProfile`: 公開プロフィール設定

AI や外部連携はすべてオプションです。コア機能がこれらの存在を前提にしないよう、参照関係は疎に保ちます。

---

## 4. 参照関係の基本ルール

### 4.1 契約を稼働系の起点にする

稼働記録と月次稼働報告は `Contract` を起点に参照します。`Project` や `Engineer` に直接ぶら下げると、どの契約条件で計算すべきかが曖昧になるためです。

`PaymentNotice` のような将来機能も同じ原則に従いますが、MVP ではまず `WorkRecord` と `WorkReport` の参照先として `Contract` を固定することを優先します。

### 4.2 クライアント向けとエンジニア向けの確定データを分ける

`Invoice` はクライアント向け、`PaymentNotice` はエンジニア向けで役割が違います。片方を流用して他方を表現しません。金額や対象月が同じでも、宛先と履歴責務が異なるからです。

### 4.3 見込みデータと確定データを混ぜない

`EngineerLead` は正式登録前の一時的な母体です。面談結果や初回連絡履歴を残せても、契約や稼働記録に直接参加させません。正式登録後に必要項目だけを `Engineer` 側へ引き継ぎます。

---

## 5. 履歴保持の原則

Tulpa では、契約・稼働・請求支払に影響する変更は「最新値だけ」にしません。最低でも次の履歴は保持対象です。

- 契約条件の履歴
- 稼働記録の修正履歴
- 月次稼働報告の状態遷移
- AI 下書きの生成履歴
- 面談メモ、営業アプローチ履歴

特に `WorkRecordRevision` と `contract_party_type` の詳細は [契約管理・稼働記録の設計メモ](../notes/contract-work-record-design.md) を参照します。

履歴保持の判断基準は次の 2 点です。

1. 後から「なぜこの金額・この状態になったか」を説明する必要があるか
2. 編集可能な最新値とは別に、過去時点の事実を残す必要があるか

## 6. MVP と将来拡張の境界

### 6.1 MVP で厚く扱うもの

- `User`
- `EngineerLead`
- `Engineer`
- `Client`
- `ClientContact`
- `Project`
- `Contract`
- `WorkRecord`
- `WorkReport`
- `InterviewNote`
- `SkillSheet`

これらは MVP / Phase 1 のコア機能を支えるため、最初から責務をはっきりさせます。

`OrderDocument` は契約管理の添付として有用ですが、MVP では契約条件の登録を優先し、注文書 PDF 添付は「初期対応候補」として扱います。添付を入れる場合でも、契約本体の成立要件にはしません。

### 6.2 将来拡張として疎結合に置くもの

- `OrderDocument`
- `PaymentNotice`
- `Invoice`
- `EngineerApproach`
- `ClientApproach`
- `ActivityLog`
- `AiMatchingLog`
- `EngineerActivity`
- `PublicProfile`

要件上は全体構想に含まれますが、Phase 2 以降のため、MVP 実装時点では先回りした複雑な共通化を避けます。

## 7. 実装時の判断メモ

### 7.1 Enum を優先する

ロール、契約当事者種別、稼働報告ステータス、面談結果、連携サービス種別のように閉じた選択肢は Enum で固定します。自由文字列は運用ドリフトを起こしやすいため避けます。

### 7.2 添付ファイルは本体から分離する

注文書、登録フォーム添付、月次報告アップロードファイル、将来の PDF 出力物は、本体レコードに巨大なメタデータを抱え込ませず、パスまたは添付専用モデルで扱います。

### 7.3 後から集計しやすいキーを失わない

クライアント別、案件別、エンジニア別、対象月別で追えることが重要です。履歴テーブルでも最低限これらのキーを辿れる設計を維持します。

---

## 8. 受け入れ条件

1. `Client` と `Project` を起点に契約、稼働、提案活動の文脈を追える。
2. 稼働系データが `Contract` に紐付き、契約条件と切り離されていない。
3. 見込みエンジニアと正式登録済みエンジニアのデータ責務が分離されている。
4. MVP と将来拡張の境界が明確で、Phase 2 以降のモデルを理由に MVP の複雑性を先取りしていない。
