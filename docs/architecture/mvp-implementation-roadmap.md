# MVP 実装ロードマップ

この文書は、Tulpa の MVP を AI 自走で実装していくための段階計画です。設計書をそのまま実装へ落とすのではなく、マイルストーン単位で機能を束ね、各マイルストーンのチェックリストが埋まったら完了と判断できる形にします。

この文書は WBS の起点として扱います。個別タスクに着手するときは、このロードマップを元に ExecPlan を作成します。

---

## 1. 使い方

進め方の原則は次の通りです。

1. まずマイルストーンを1つ選ぶ
2. マイルストーン配下の作業項目を、実装単位ごとの ExecPlan に分ける
3. 各 ExecPlan で、参照文書、MVP 境界、未決事項確認を残す
4. チェックリストがすべて埋まり、完了条件を満たしたらそのマイルストーンを完了とする

この文書は「全部を一度に実装する計画」ではなく、「どの順に実装すると手戻りが少ないか」を固定するための文書である。

---

## 2. 実装順の考え方

MVP は次の 3 段階で進める。

1. `土台を作る`
   認証、ロール、主要エンティティ、基本ナビゲーションなど、後続の全機能が依存する基盤を作る。
2. `業務フローを通す`
   稼働記録から月次稼働報告まで、Tulpa の中核フローを end-to-end で成立させる。
3. `MVP の入口と運用性を整える`
   招待、PWA、年間カレンダーなど、MVP として公開できる完成度まで整える。

この順にする理由は、権限・データモデルが固まる前に業務フローを実装すると手戻りが大きく、逆に業務フローが通る前に周辺 UX を詰めても検証しにくいためである。

---

## 3. マイルストーン一覧

| マイルストーン | 目的 | 主な成果物 |
|------|------|------|
| M1. 基盤と主要データ | 実装の土台を固定する | 認証、4 ロール、主要モデル、基本画面枠 |
| M2. 稼働記録と月次報告 | 中核フローを end-to-end で成立させる | 稼働記録入力、月次提出、差戻し、確認 |
| M3. MVP 公開準備 | 招待・閲覧・運用の入口を整える | 招待フロー、スキルシート、PWA 基本、年間カレンダー |

## 4. マイルストーン詳細

## 4.1 M1. 基盤と主要データ

目的:
後続のすべての実装が依存する土台を揃える。ここでは「Tulpa のデータと権限の骨格がある」状態を作る。

参照文書:

- [../requirements.md](../requirements.md)
- [access-control-and-roles.md](./access-control-and-roles.md)
- [data-model.md](./data-model.md)
- [ui-and-screen-design.md](./ui-and-screen-design.md)
- [open-questions.md](./open-questions.md)

作業項目:

- [ ] 認証方式と 4 ロールの基本方針を確定する
- [ ] ユーザーとロールの永続化モデルを実装する
- [ ] `Client`, `ClientContact`, `Engineer`, `EngineerLead`, `SkillSheet`, `Project`, `Contract` の MVP モデルを実装する
- [ ] MVP 対象の Enum と基本制約を実装する
- [ ] 一覧・詳細画面の土台になる共通レイアウトとロール別ナビゲーションを用意する
- [ ] オーナー、エージェント、エンジニア、クライアント担当者のアクセス境界をルートと画面で確認できる状態にする

このマイルストーンでやらないこと:

- 稼働記録の状態遷移
- 月次報告の確認フロー
- 支払通知、請求書、AI マッチング

完了条件:

- ログイン後にロール別の基本導線へ入れる
- 主要エンティティの作成、一覧、詳細の最低限の土台がある
- 権限境界に反した画面閲覧や操作ができない
- 後続のワークフロー実装に必要なモデルと関連が揃っている

想定する ExecPlan の分割例:

1. 認証・ロール基盤
2. クライアント・案件・契約の基礎モデル
3. エンジニア・スキルシート・見込み登録の基礎モデル
4. ロール別レイアウトとナビゲーション骨格

## 4.2 M2. 稼働記録と月次報告

目的:
Tulpa の中核である「エンジニアが記録し、月次で提出し、クライアント担当者が確認する」流れを成立させる。

参照文書:

- [../requirements.md](../requirements.md)
- [data-model.md](./data-model.md)
- [workflows/work-record-and-report-design.md](./workflows/work-record-and-report-design.md)
- [workflows/project-contract-lifecycle.md](./workflows/project-contract-lifecycle.md)
- [ui-and-screen-design.md](./ui-and-screen-design.md)
- [open-questions.md](./open-questions.md)

作業項目:

- [ ] `WorkRecord`, `WorkRecordRevision`, `WorkReport`, `WorkReportComment` の MVP モデルを実装する
- [ ] `1契約・1日・1件` の稼働記録ルールを守る入力・編集 UI を実装する
- [ ] 作業開始・作業終了の即時記録フローを実装する
- [ ] 記録漏れ時の手動入力と修正履歴保持を実装する
- [ ] 月次稼働報告の作成、提出、差戻し、確認フローを実装する
- [ ] エンジニア、エージェント、クライアント担当者ごとの画面表示差分を実装する
- [ ] 契約期間外の記録や確認対象外データを防ぐ検証を実装する

このマイルストーンでやらないこと:

- 精算幅に対する厳密な自動計算
- 支払通知や請求書との連動
- 日跨ぎ稼働、複数セッション、オフライン同期

完了条件:

- エンジニアがスマホ前提で稼働記録を入力できる
- エンジニアが対象月の稼働報告を提出できる
- クライアント担当者が確認または差戻しできる
- 差戻し後に必要範囲だけ修正して再提出できる
- 主要状態 `draft / submitted / returned / confirmed` が画面とデータで一致している

想定する ExecPlan の分割例:

1. 稼働記録モデルと開始・終了記録
2. 稼働記録の編集と修正履歴
3. 月次稼働報告フロー
4. クライアント担当者向け確認画面

## 4.3 M3. MVP 公開準備

目的:
MVP として公開・試用しやすい入口と運用性を整える。ここでは中核フローを補強する周辺機能を追加する。

参照文書:

- [../requirements.md](../requirements.md)
- [access-control-and-roles.md](./access-control-and-roles.md)
- [ui-and-screen-design.md](./ui-and-screen-design.md)
- [workflows/project-contract-lifecycle.md](./workflows/project-contract-lifecycle.md)
- [open-questions.md](./open-questions.md)

作業項目:

- [ ] エンジニア招待とクライアント担当者招待の MVP フローを実装する
- [ ] エンジニア登録フォームと見込み登録から正式登録までの導線を実装する
- [ ] スキルシート編集の MVP 画面を実装する
- [ ] 年間カレンダービューを実装する
- [ ] PWA の基本対応を実装する
- [ ] MVP で必要な通知のみ実装する
- [ ] 初回利用時に主要導線を辿れる最低限のダッシュボードを整える

このマイルストーンでやらないこと:

- 契約更新アラートの本格運用
- 記録漏れ通知の自動化
- AI マッチング、CRM、外部連携、公開プロフィール

完了条件:

- エージェントがエンジニアとクライアント担当者を招待できる
- エンジニアがスキルシートと契約・稼働導線を自力で辿れる
- クライアント担当者が確認に必要な最小画面へ辿れる
- スマホのホーム画面追加と MVP 必要範囲の通知が機能する
- 年間カレンダーで月次の稼働状況を俯瞰できる

想定する ExecPlan の分割例:

1. 招待と初回登録
2. スキルシート編集
3. 年間カレンダー
4. PWA 基本対応

---

## 5. WBS へ落とすときの粒度

1 つの ExecPlan は、原則として「1〜4 ファイル」ではなく「1 つの動く単位」で切る。目安は次の通り。

- 1 つの主要画面とその背後のサービス
- 1 つの状態遷移
- 1 つの主要モデル群とその migration
- 1 つの招待または登録フロー

逆に、次の単位は大きすぎる。

- `稼働記録を全部作る`
- `契約管理を全部作る`
- `MVP を全部実装する`

---

## 6. マイルストーン完了の判定

マイルストーン完了は、単にコードが存在することではなく、次を満たしたときとする。

1. この文書の対象チェックリストがすべて埋まっている
2. 各 ExecPlan の `Validation and Acceptance` が確認済みである
3. 関連する `open-questions.md` の項目が、未解決のまま実装を阻害していない
4. MVP 対象外の機能が紛れ込んでいない

---

## 7. 次の着手候補

最初の ExecPlan は、次のどちらかから始めるのが安全である。

1. `M1-1 認証・ロール基盤`
   理由: 後続の全画面と認可が依存するため。
2. `M1-2 クライアント・案件・契約の基礎モデル`
   理由: 稼働記録と月次報告の参照先になるため。

どちらを先にしてもよいが、最初の 2 本は M1 の中で連続して進める。
