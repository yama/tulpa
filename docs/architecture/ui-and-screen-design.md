# 画面設計と主要導線の整理

このドキュメントは [要件定義書](../requirements.md) の 5 章「画面設計」を、ロール別の導線と画面責務が追いやすい形に整理した補助設計書です。実装前に「この画面はどこにあるのか」「誰が何をする画面か」を確認する入口として使います。

---

## 1. 対象範囲

このメモでは次の内容を扱います。

1. 画面設計の全体方針
2. ロール別の主要画面
3. 主要導線とナビゲーション
4. MVP で最小構成に留める画面

コンポーネント単位の見た目や CSS 詳細、Blade テンプレート分割方針はここでは扱いません。

---

## 2. 全体方針

Tulpa の画面設計は「情報をたくさん見せる」ことより、「今必要なことだけを迷わず処理できる」ことを優先します。特にログイン直後の画面は、ロールごとの次アクションを中心に組み立てます。

共通方針は次のとおりです。

- スマホファーストで設計する
- 詳細は案件・クライアント・契約の文脈へ潜る形にする
- ダッシュボードは行動の起点であり、情報倉庫にしない
- htmx 前提で、画面遷移より部分更新を活かせる構造を選ぶ

---

## 3. ロール別の主要画面

### 3.1 エンジニア

主要画面は次の 4 つです。

- ダッシュボード
- 稼働記録と年間カレンダー
- 契約詳細
- プロフィールと設定

ダッシュボードでは、今月の稼働状況、作業開始・作業終了ボタン、差戻しの有無だけを優先表示します。契約詳細では、契約条件と月次稼働報告へ辿れるようにします。MVP のプロフィールと設定は、スキルシートと口座設定を中心にします。

### 3.2 エージェント

MVP の主要画面は次の 3 つです。

- ダッシュボード
- クライアント中心ビュー
- エンジニア中心ビュー

エージェントのダッシュボードは「対応が必要なものだけを見る」前提です。クライアント中心ビューとエンジニア中心ビューは、それぞれ契約管理と初回接点管理の入口になります。AI マッチング画面は Phase 3 以降の追加画面として扱います。

### 3.3 クライアント担当者

MVP では最小構成に留めます。

- 稼働報告一覧
- 稼働報告詳細
- 差戻しコメント入力

確認フローに不要な契約詳細や営業情報は持ち込みません。

---

## 4. 主要導線

### 4.1 エンジニア導線

ログイン直後の最短導線は次のとおりです。

1. ダッシュボードで今月の状況を見る
2. 作業開始または作業終了を記録する
3. 必要なら稼働画面で不足分を補完する
4. 月末に月次稼働報告を提出する

### 4.2 エージェント導線

ログイン直後の主な導線は次のとおりです。

1. ダッシュボードで未対応の登録者と確認待ちを確認する
2. クライアントまたはエンジニア詳細へ遷移する
3. 必要に応じて契約、面談メモ、初回連絡履歴を更新する

Phase 2 以降:

1. 契約更新アラートや次アクションをダッシュボードで確認する
2. クライアントまたはエンジニア詳細で営業情報を更新する

Phase 3 以降:

1. 案件に対して候補者を確認する
2. AI サマリーを仕上げる

### 4.3 クライアント担当者導線

1. 確認待ちの稼働報告一覧を見る
2. 詳細を開いて内容を確認する
3. 確認または差戻しを行う

---

## 5. ナビゲーション

### 5.1 エンジニア

スマホ基準で下部タブナビゲーションを使います。

| タブ | 内容 |
|------|------|
| ホーム | ダッシュボード |
| 稼働 | 稼働記録・年間カレンダー |
| 契約 | 契約詳細・月次稼働報告 |
| プロフィール | スキルシート・口座・設定 |

### 5.2 エージェント

エージェント画面は PC 利用も想定し、一覧と詳細を行き来しやすい構造を優先します。ナビゲーション項目は少なくとも次を想定します。

- ダッシュボード
- クライアント
- エンジニア

Phase 2 以降:

- 案件

Phase 3 以降:

- マッチング

---

## 6. MVP で最小構成に留める画面

初期版で広げすぎないため、次は最小構成で扱います。

- クライアント担当者向けの追加ポータル画面
- CRM の詳細分析画面
- 外部サービス連携データの可視化ダッシュボード
- 公開プロフィールの高度な閲覧分析画面
- AI マッチング専用画面

クライアント担当者向けは、MVP では `稼働報告一覧` `稼働報告詳細` `差戻しコメント入力` の 3 画面だけを持ちます。

画面が必要になっても、まずは対象ロールの主要導線に統合できないかを検討します。

---

## 7. 受け入れ条件

1. ロールごとに主要画面と主目的を説明できる。
2. エンジニア、エージェント、クライアント担当者の主要導線が 3 ステップ程度で追える。
3. 画面設計が「今必要なことだけを見せる」方針と矛盾していない。
4. クライアント担当者向け画面が MVP で最小構成に抑えられている。
