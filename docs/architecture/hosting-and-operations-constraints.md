# ホスティング・運用制約

この文書は、Tulpa を一般的なレンタルサーバまたは小規模 VPS で運用する前提で、実装時に守るべき制約を整理するための設計メモです。さくらインターネット、ロリポップのような一般的な共有ホスティングで破綻しないことを優先します。

この文書が答えること:

- どのようなホスティング環境を前提にするか
- MVP 実装で避けるべきインフラ依存
- バックグラウンド処理、添付ファイル、通知の扱い方
- 実装時に「便利だが重い」仕組みをどこまで採用しないか

この文書が答えないこと:

- 特定レンタルサーバ会社ごとの詳細な設定手順
- 本番デプロイ手順の手順書
- 将来の高負荷構成や大規模マルチテナント構成

関連する SSOT:

- [requirements.md](../requirements.md)
- [open-questions.md](./open-questions.md)

## 1. 前提

Tulpa の MVP は、次のような環境で動かせることを前提とする。

- PHP 8.2 以上が使える
- MySQL 8.0 以上または MariaDB 10.6 以上が使える
- Composer ベースでアプリを配置できる
- Cron を最低限設定できる、または Cron なしでも致命的に破綻しない
- Node.js 常駐や常時稼働ワーカーを前提にしない
- Redis、Elasticsearch、SQS、専用メッセージブローカーを必須にしない

MVP の評価基準は、「小規模エージェント会社が一般的なレンタルサーバで導入しやすいか」です。高機能な構成を先に前提化しません。

---

## 2. 基本方針

### 2.1 常駐プロセスを必須にしない

Tulpa のコア機能は、Web リクエストと通常の DB アクセスだけで成立する形を優先する。

- queue worker の常駐を前提にしない
- WebSocket サーバ常駐を前提にしない
- Supervisor や systemd のようなプロセス管理を必須にしない

通知、AI 連携、重い集計などは将来の拡張として追加できても、未設定時にコア機能が壊れない構成を保つ。

### 2.2 ビルド不要を維持する

フロントエンドは、レンタルサーバへそのまま配置できる構成を優先する。

- Alpine.js + htmx を CDN 読み込みで使う
- Tailwind CSS はビルド済みファイルを同梱する
- Node.js を本番サーバで動かすことを前提にしない
- SSR を崩す重いフロントエンドフレームワークを持ち込まない

### 2.3 オプション機能は必須にしない

Claude API、Slack API、PWA 通知はオプション機能として扱う。

- 未設定なら UI ごと非表示または無効化する
- API 障害時もコア画面を継続利用できるようにする
- 外部 API 呼び出し結果に業務の主データを依存させない

## 3. 実装時の禁止事項と注意点

### 3.1 MVP で避ける実装

MVP では次を避ける。

- Redis 前提のキャッシュ・キュー・ロック
- queue worker 常駐前提の画面機能
- WebSocket 前提のリアルタイム通知
- Node.js 必須の本番アセットビルド
- headless Chrome 常駐前提の PDF 生成
- ローカル以外の専用オブジェクトストレージ必須化
- 大量データを前提にした複雑な検索基盤

採用する場合は、「なくても MVP が成立する代替経路」を先に持つこと。

### 3.2 Laravel 機能の使い方

Laravel を使うが、共有ホスティングで重くなりやすい使い方は避ける。

- Queue は `sync` または `database` を初期前提とする
- Cache は `file` を初期前提とする
- Session は `file` または `database` を初期前提とする
- Broadcast は MVP では使わない
- Reverb / Echo のような常駐型リアルタイム基盤は MVP で採用しない

`php artisan schedule:run` を 1 分ごとに回せる環境は望ましいが、使えない環境でもコア機能が破綻しないようにする。通知・リマインド類は Cron 依存を持ち込む前に、手動実行や画面上の注意表示で代替できるかを優先する。

### 3.3 添付ファイルと公開パス

共有ホスティングでは公開ディレクトリ制約が強い場合があるため、添付ファイルは次を前提にする。

- MVP の添付は最小限に絞る
- Laravel の `storage` を基本にする
- `storage:link` が使えない環境を想定し、公開方法を README または導入手順に明記できる設計にする
- 機密ファイルを `public/` に直置きしない
- 契約添付やプロフィール添付は、権限確認を通した配信を優先する

### 3.4 メールと通知

メール送信は使うが、失敗時の劣化動作を用意する。

- 招待メールや受付完了メールは再送可能にする
- 送信失敗で主データ作成自体をロールバックしない
- 通知送信履歴や失敗理由を最低限確認できるようにする
- PWA 通知は補助導線であり、通知が届かなくても画面で回復できるようにする

## 4. MVP で採る運用前提

### 4.1 バックグラウンド処理

MVP では、バックグラウンド処理の有無で二段階に考える。

- コア機能: 同期処理で完結する
- 補助機能: Queue や Cron があれば便利だが、なくても手動運用で吸収できる

例:

- 稼働記録保存、月次稼働報告提出、確認フロー: 同期処理
- 招待メール送信: 同期でも成立、将来は Queue 化可能
- 記録漏れ通知、契約更新アラート: Phase 2 以降

### 4.2 バックアップとログ

バックアップとログは、レンタルサーバでも最低限回る前提に寄せる。

- 日次バックアップを前提とする
- DB バックアップと添付ファイル退避を分けて考える
- 詳細な監視 SaaS を前提にしない
- まずはアプリケーションログと障害把握手段を整える

復元目標時間、保持世代数、ログ保持期間、障害通知先は [open-questions.md](./open-questions.md) の `未解決` として扱う。

### 4.3 デプロイと配布

MVP の配布形態は次を優先する。

- ZIP ダウンロードで配置できる
- Git が使える環境では Git デプロイも可能
- セットアップ時に特殊なサーバ権限を要求しない

この前提により、導入手順は「Composer で依存を入れる」「`.env` を設定する」「DB を migrate する」程度に収める。

---

## 5. 共有ホスティング前提での判断基準

新しい技術や仕組みを追加するときは、次で判断する。

1. その機能は MVP のコア価値に直結しているか
2. 常駐プロセスや外部インフラがなくても成立するか
3. 代替として手動運用や同期処理に落とせるか
4. 導入手順が「一般的な PHP アプリの設置」から大きく逸脱しないか
5. API 未設定や Cron 未設定でも、主機能が壊れないか

1 つでも厳しい場合は、MVP では持ち込まない。

---

## 6. 実装前チェック

この前提でコードを書く前に、次を確認する。

1. その機能は共有ホスティングで同期処理として成立するか
2. Queue、Cron、Redis、Node.js を暗黙に前提にしていないか
3. 添付ファイルや通知が失敗しても主データの保存が成立するか
4. オプション機能未設定時の UI と挙動が定義されているか
5. 導入手順に特殊権限や常駐プロセスが必要になっていないか

判断に迷う場合は、まずこの文書と [open-questions.md](./open-questions.md) を更新する。
