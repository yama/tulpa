# 業務委託運用の法務ガードレール

このメモは、Tulpa が扱うフリーランス業務委託の運用を、雇用・派遣を前提としたプロダクト設計に寄せないための補助設計メモです。

Tulpa は人材派遣管理システムではなく、業務委託契約に基づく案件・契約・稼働記録・月次稼働報告を扱う OSS です。したがって、機能追加や UI 設計では「便利そう」より先に、指揮命令関係を示唆しないことを優先します。

この文書は法的助言そのものではなく、要件・UI・権限・実装判断をぶらさないための設計メモです。最終的な契約実務や運用判断は、必要に応じて専門家確認を前提とします。

---

## 1. 背景

要件定義書では、フリーランスエンジニアは業務委託契約に基づく個人事業者であり、時間・場所による指揮命令関係は発生しない前提を採っています。

- `勤怠` ではなく `稼働記録`
- `打刻` ではなく `作業開始` / `作業終了`
- クライアントによる `承認` ではなく `確認`

この方向性は、Tulpa の言葉遣いを整えるだけでなく、実際のプロダクト挙動が雇用管理や派遣運用に見えないことまで含みます。

---

## 2. 守るべき原則

### 2.1 クライアントは指揮命令者ではない

Tulpa 上でクライアント担当者が行うのは、月次稼働報告の確認と差戻しまでです。日々の業務遂行方法、労働時間、休憩、休日、配置変更を管理する主体として扱ってはいけません。

### 2.2 エンジニア本人が入力主体である

稼働記録は、エンジニアが自律的に記録する業務ログとして扱います。未入力是正や時刻修正の強制を、クライアント主導の運用として組み込んではいけません。

### 2.3 契約当事者と責任分界を曖昧にしない

Tulpa は契約条件を管理するが、Tulpa 自体が契約上の指揮命令関係を作るべきではありません。`agent_client`、`agent_engineer`、`client_engineer_direct` の区別は、請求・支払だけでなく責任分界の曖昧化を防ぐためにも維持します。

### 2.4 月次確認フローは内容整合の確認に限定する

差戻しは、対象月、合計稼働時間、添付ファイル、記録漏れや明細不整合の確認のために使います。日々の作業方法や現場での振る舞いを是正するためのフローに変質させてはいけません。

---

## 3. プロダクトに落とす判断ルール

### 3.1 用語

次の語は、UI、コード、通知文面、ヘルプ文言で使いません。

- 勤怠
- 打刻
- 出勤
- 退勤
- 勤務時間
- 承認
- 遅刻
- 早退
- 欠勤承認

代わりに次を使います。

- 稼働記録
- 作業開始
- 作業終了
- 稼働時間
- 確認
- 差戻し

### 3.2 クライアント担当者に持たせない機能

MVP および将来拡張でも、クライアント担当者向けに次の機能を安易に追加しません。

- 始業・終業・休憩・休日の指示や固定
- 日次の出欠管理
- 遅刻、早退、欠勤の登録や承認
- 作業方法や遂行手順への直接指示
- エンジニアの配置変更や差し替え操作
- 未入力に対する督促命令
- 日次の評価、査定、勤務態度管理

### 3.3 許容する機能

次は、業務委託運用に沿う範囲で許容されます。

- エンジニア本人による稼働記録の入力と後修正
- 月次稼働報告の提出
- クライアント担当者による月次稼働報告の確認
- 明細不整合に対する差戻しコメント
- 現場指定フォーマットの添付確認
- 契約期間内かどうかの入力制御

### 3.4 通知の扱い

クライアント担当者を、エンジニアに対する日常的な督促主体として扱いません。通知の主語は、原則としてシステムまたはエージェントとし、クライアントからの拘束的な是正要求に見える文面を避けます。

---

## 4. 画面設計と権限への影響

### 4.1 クライアント画面

クライアント担当者画面は、確認待ちの月次稼働報告を処理する最小画面に留めます。契約単価、支払条件、内部メモ、他案件情報、他社情報を見せません。

また、稼働記録の粒度を見せる場合でも、業務遂行の監督画面に見えないよう注意します。月次報告の整合確認に不要な日次監視 UI は持ち込みません。

### 4.2 エンジニア画面

エンジニア画面では、自律入力を支えることを優先します。

- 即時記録
- 後入力
- 修正履歴
- 提出前確認
- 差戻し対応

これらは許容されますが、雇用管理アプリのような出欠・遅刻・残業警告に寄せません。

### 4.3 エージェント画面

エージェントは案件・契約・稼働報告の文脈を横断して扱いますが、クライアントの指揮命令を代替するようなタスク管理 UI を持ち込まないようにします。Tulpa の中心は、契約・稼働・請求支払の文脈統合であり、現場作業の管理ではありません。

---

## 5. 実装レビューでのチェックポイント

機能追加や画面追加のレビュー時は、少なくとも次を確認します。

1. クライアント担当者に、労働時間や作業方法を直接管理する操作を与えていないか
2. 文言が `確認` ではなく `承認` や `勤怠` に戻っていないか
3. エンジニア本人の自律入力を前提としたフローが崩れていないか
4. 差戻しコメントが、月次報告の整合確認を超えて現場指示に使われる設計になっていないか
5. `client_engineer_direct` を含む契約種別で、責任分界が曖昧になる UI になっていないか
6. 通知文面が、クライアントによる拘束的命令や出勤管理のように読めないか

---

## 6. 当面の運用方針

MVP では、次を明示的に対象外または運用吸収とみなします。

- クライアントによる日次勤怠管理に相当する機能
- シフト管理
- 遅刻・早退・欠勤ワークフロー
- 現場での詳細タスク指示や評価フロー
- クライアント主導の未入力督促自動化

これらが必要という要望が出ても、まずは「本当に Tulpa が扱うべきか」を再確認し、業務委託運用と矛盾しないかを設計書で先に固定します。
